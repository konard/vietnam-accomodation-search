## Findings and acceptance limits

The poster false negative and the incomplete-history success/warning defect reproduce without private data. The new tests fail on the original code. The implementation fixes both shared production paths and adds durable public-preview pagination. Original source text and real binary verification remain required. A separate native-clink projection probe tests full-body synthetic ledgers; its performance results are recorded below.

**Release acceptance is blocked.** Repository Actions secrets, Actions variables and GitHub releases are empty. Actual release-mode preflight fails with zero verified, two failed and one unknown local probe: the absent npm package needs an authorized bootstrap `NPM_TOKEN`; Docker Hub image/account/token configuration is absent; local execution has no Actions OIDC token. The real main release run [37572369835](https://github.com/konard/vietnam-accomodation-search/actions/runs/37572369835) independently reports the two publishing failures. This PR does not create credentials, change publication settings, claim a token rotation, or replace publication evidence with a local build. The separate Telegram account proposal is unnecessary.

**Private-data acceptance is pending.** The retained real poster, protected source journal and authenticated Telegram session used in the independent retest are unavailable in this checkout. Sanitized poster controls, routed self-authored Chromium pages and synthetic ledgers are explicitly identified as such. They do not certify the original real-image fields, the protected 368-offer source, or the complete protected cohort. Those gates remain open until an authorized environment produces the evidence. Separate read-only live public-preview evidence reaches the 90-day cutoff across collector restarts, as recorded below; it does not establish whole-catalog or authenticated private-history coverage. No source bodies, contacts, usernames, message identifiers or credentials from a private corpus are published here.

## Root causes and implementation

### Poster reconciliation

Production OCR was already wired in PR 141, including Tesseract sparse-text PSM 11. The independent real-image report says this configuration recovers the 13M VND/month poster, while reconciliation rejects it because a second regular expression requires a literal rental verb. The price parser already marks this poster's price as rent with period month. Its structured evidence is sufficient to proceed through the existing housing classification and provisional review process.

The guard now accepts a price option when it has rent/period evidence and either the text expresses rental intent or the option itself is identified as rent. The explicit-intent alternative matters: a valid English rental with `9 million VND/month` can have `period=month` while its price option's `rent` flag is false. Removing that alternative regresses an existing media contract. No numeric correction or fixture-specific string is introduced.

`tests/issue-144-poster.test.js` reproduces the original rejection, verifies 13,000,000 VND/month with retained photos/extraction provenance, and checks maps, receipts, sales, requests, malformed OCR prices and vehicle rentals. Existing production OCR, cancellation, captioned-album and field-accuracy suites cover the routes using this shared function.

### Public history

`BrowserCollector` correctly attached `historyComplete=false`, but `runSourcePool` classified the array solely by its length. `summarizeOutcomes` then counted offers/empty as success, and the bot skipped its failure formatter when `summary.failed=0`. These are separate propagation errors. Also, merely avoiding a new success timestamp was insufficient when a prior complete scan had left a fresh timestamp in the collection state.

The outcome is now `partial` with category `incomplete-history`. Aggregate summaries expose an optional `incomplete` count and do not credit that history as successful. Partial results do not trigger the inaccurate "No fresh offers" message. The formatter also recognizes legacy offers/empty outcomes carrying `historyComplete=false`, including stale summaries. Cache-first reports load persisted incomplete states, warn while refresh runs, and keep the incomplete source eligible for another bounded slice. An explicitly cache-only `refresh: false` search also reports known incomplete history without starting a refresh; a separate before/after control reproduces that otherwise omitted warning.

Final call-site review reproduced an additional delivery gap: when no offer matches, the bot's `/search` handler sends only its no-current-offers message even though the formatter returns an incomplete-history warning. The handler now includes that warning in its bounded empty-result reply. It also safely accepts cached reports without a summary. A failing-before/passing-after command-handler test covers partial, legacy empty/stale-summary and cache-first/no-summary reports, and checks that none incorrectly announce "No fresh offers".

The public-preview checkpoint is committed after `onSourceComplete` saves the slice. Failed persistence leaves the older cursor available for replay. A complete scan next visits the latest page and stops when it overlaps known coverage; an unfinished scan resumes `before=<oldest-id>`. The cutoff is frozen for the backfill, and advancing the rolling window does not invalidate already-covered older history. A mismatched/future window or malformed saved checkpoint is reset safely.

`tests/issue-144-history.test.js` covers aggregate/legacy/cached reporting, empty results, restart, boundary completion, future windows, failed checkpoint writes and stale scheduling. `experiments/issue-142-browser-resume.mjs` additionally exercises real Chromium navigation and DOM extraction with self-authored pages. The first report contains one cached offer and an incomplete-history warning; the second collector visits `?before=80`, returns complete empty history and retains the cached offer.

`experiments/issue-142-live-preview.mjs` then reads public channels identified in #142 without authentication, intercepted pages or messaging. It accepts an environment-provided public preview URL, limits the probe to 1–12 collector instances and 1–10 pages per instance, uses the application's navigation/source budgets and deletes its private temporary store after closing Chromium. Each instance opens a new `LinksStore` and collector, so progress must reload from durable state. Output contains aggregate counts, ages, statuses and timings; it contains no message bodies, source names or message IDs. These browser controls use the production text store/checkpoint route; actual binary durability is verified separately by mandatory clink tests and the full-body profile.

### Full-body projection

The protected report describes 368 offers expanding into 110,291 domain records, about 29.68 MB of JSON and 406 trace rows. Offer count alone is a poor proxy for projection cost. The pinned clink source represents each named reference through character/Unicode links in a companion database; uniqueness/update operations scan storage. Repeated long field paths and source text multiply that work. Simply raising shard size worsens this cost.

The projection now uses a reversible per-shard table of original string identifiers and clink's native numeric addresses for long-name shards. The schema, canonical text and public record values remain unchanged. Aliases are private durable files included in the manifest hashes and adoption/reuse verification. Import/export must pass twice: first against the compact input, then after expanding every exported address against the original canonical links. An unknown address or dropped/rewritten link fails closed. Existing small-name fixtures and old verified manifests remain readable.

Numeric projections avoid character-link expansion, so their default minimum/average/maximum shard sizes become 128/256/512 to amortize process launches and durable files. Ordinary short-name projections retain 32/64/128, and explicitly configured bounds take precedence. A changed layout is rebuilt as derived storage through the existing verified atomic adoption path; it does not change the canonical ledger or discard the previous verified candidate before its replacement succeeds.

The existing audit source journal already records fetched/parsed work before projecting it, and only marks completion after verified persistence. Tests in `tests/issue-108-audit-progress.test.js` replay an interrupted projection without refetching, keep passes independent and reuse a completed source. The new alias tests verify complete original text, numeric-looking/Unicode names, corrupt-table repair, unchanged reuse and invalid-address rejection. The real-clink integration tests retain normalization, canonical round-trip, changed-shard and corruption checks.

## Performance and reproducible commands

Exploratory baseline with four self-authored full-body offers produces 996 domain records and 243,279 JSON bytes. Actual clink imports at the original name representation took 21,595 ms at max 128 links (230 imports), 51,549 ms at max 512 links (58 imports), and 299,223 ms at max 2,048 links (12 imports). These sequential, finite probes show why enlarging named shards is insufficient. The intermediate short-string-alias prototype remained costly; native numeric-address profiling and final validation are recorded in the accompanying verification results.

After all local suites and the overlapping exploratory run finished, sequential isolated numeric-address probes measured:

| Offers | Maximum shard links | Domain records | JSON bytes | Imports | Verified persistence | Verified readback | Total      |
| ------ | ------------------- | -------------- | ---------- | ------- | -------------------- | ----------------- | ---------- |
| 4      | 128                 | 996            | 243,279    | 230     | 12,382 ms            | 3,190 ms          | 15,576 ms  |
| 4      | 256                 | 996            | 243,279    | 114     | 14,358 ms            | 2,704 ms          | 17,065 ms  |
| 4      | 512                 | 996            | 243,279    | 58      | 6,734 ms             | 2,276 ms          | 9,014 ms   |
| 368    | 512                 | 91,632         | 22,388,194 | 5,625   | 582,931 ms           | 207,975 ms        | 792,111 ms |

Every probe returned all records unchanged. The 512-link numeric projection reduced the four-offer persistence time from the original representation's 21,595 ms at its default 128 links to 6,734 ms. These single-run timings inform the bounded default; they are not a statistical benchmark or a private-corpus acceptance result. `importMs` in the experiment sums overlapping child-process durations and is not wall-clock time.

The isolated full-size synthetic ledger completes verified persistence in 9.72 minutes and restored-record readback in 3.47 minutes (13.20 minutes total). No other local test suite or native projection ran during this measurement. Fixture generation and final temporary-file cleanup are outside the reported persistence/readback timers. This demonstrates a finite full-body workload with actual binary storage; the larger protected source and complete private cohort still require their own execution.

The exploratory 368-offer numeric run at 128 links produced 91,632 records and 22,388,194 JSON bytes, needed 21,630 imports, persisted in 1,279,071 ms (21.32 minutes) and returned all records unchanged. Local coverage/runtime suites overlapped that run, so its elapsed time cannot establish an isolated full-size improvement. The synthetic ledger also has fewer records/bytes than the protected 110,291-record, 29,681,658-byte ledger. Ten-second CPU samples identified process launches during projection and parsing/garbage collection during the later readback; restoring and reading the full ledger must remain part of verification.

The finite generator allows 1–368 offers and 32–2,048 maximum shard links. Node heap is limited to 2 GiB. Temporary state is private and removed in `finally`; real clink timeouts and settled-worker behavior remain active. Initial disk headroom exceeded 80 GB, well above the independent retest's under-2-GB stop threshold. ## Completion gates

Code verification requires targeted regressions, all Node/Bun/Deno suites, complete production line coverage with actual clink 0.2.11, formatting/lint/duplication checks and exact-head PR CI. The final verification record belongs in the PR description.

External acceptance additionally requires the authorized release commit to pass real authentication/write probes, publish npm/GitHub/native OCI artifacts, verify platform digests/manifests and clean-install from the registry. Original poster/media review and full protected cohort acceptance require their private retained inputs/session and adequate isolated disk resources. Until those executions exist, the PR's required closing references do not constitute evidence that the release or protected-data gates passed.
