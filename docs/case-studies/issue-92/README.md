## Issue 90: one unbounded LiNo file per non-offer collection

Root causes, confirmed on main:

1. Only `offers` had a chunked layout (#61, #85). Every other collection (`domain-records`, `traces`, `telegram-events`, sources, settings and the rest) was written by `#saveRecords` as one `KIND.lino`. `LinkCliMirror#stage` then passed that whole text to `parseNotation`, whose `links-notation` `Parser` rejects input above `MAX_NOTATION_LENGTH = 256 MiB`. That is the crash in the issue: `parseNotation ← splitNotation ← #split ← stage`.
2. Every append was a read-modify-write of the whole collection. `TelegramIngestionService#appendRecords`, `#mergeEvents` and `TraceRecorder#persist` called `updateRecords`, which parsed the whole file, merged in memory and serialized it again. Their caps counted records only (`maxEvents * 10`), never bytes.
3. The audit (`experiments/audit-telegram-accommodations.mjs`) merged every batch into `domain-records` and `traces` this way. It also kept every domain record in memory for its final storage check.

Reproduction: `experiments/issue-90-reproduce.mjs` saves 1,000 semantic links (2.0 MiB of LiNo, about 33× a 64 KiB bound), appends one more with `updateRecords`, and reads them back, with the binary mirror on. On a main checkout with `MAX_NOTATION_LENGTH` edited to `64 * 1024`, it fails with `Input size exceeds maximum allowed size of 65536 bytes` at `links-notation` `index.js:2609 ← parseNotation (:161) ← splitNotation (:231) ← #split (:446) ← stage (:636)`, which are the frames in the issue. On this branch it prints `round-trip 1001`.

### Measurements

`experiments/issue-90-append-past-parse-cap.mjs` uses the production bound (256 MiB) and the default 4 MiB chunk size. It appends batches of 5,000 synthetic, audit-shaped semantic links (about 3 KB of LiNo each) until the collection is larger than the bound, and then streams a full read with `indexedRecordBatches`. The mirror is off, so the numbers are storage only.

| `node experiments/issue-90-append-past-parse-cap.mjs 300 5000` |                                 this branch |
| -------------------------------------------------------------- | ------------------------------------------: |
| Batches of 5,000 records appended                              |                                          21 |
| Records / collection size                                      | 105,000 / 304.8 MiB, over the 256 MiB bound |
| Chunks / largest / mean                                        |                 154 / 4,096 KiB / 2,027 KiB |
| Append time per batch: first / median / last                   |                    1,473 / 1,407 / 2,329 ms |
| Streamed read of all records, one chunk at a time              |                    105,000 records in 104 s |
| Peak RSS                                                       |                                     319 MiB |

On main, this collection is one file that `parseNotation` rejects once it is over the bound (see the reproduction above), and every save before that rewrites and stages the whole file. Here no file is larger than 4 MiB, an append touches the tail chunk only, and memory stays flat. The time per batch grows slightly with the number of chunks; this was not profiled, and the per-batch index read and write is the likely cause. The streamed read is slow (about 3 MiB/s) because every record is parsed and checked against its typed schema. It is used for full reads and the migration, not for appends.

A 10 MiB trial run gave 5,000 records, 14.3 MiB, 8 chunks, a largest chunk of 2,842 KiB and a mean of 1,829 KiB, with 1.6 s per batch and 271 MiB peak RSS.

### Options considered

- **Content-defined chunking**, as in FastCDC ([USENIX ATC 2016](https://www.usenix.org/conference/atc16/technical-sessions/presentation/xia)) and restic. A cut depends only on the record's id and size, so chunk boundaries survive inserts and deletes elsewhere, and unchanged chunks keep their digests and projections. The cut test works on whole records, because a chunk must stay valid LiNo. The FNV-1a hash of the id replaces the rolling hash.
- **A byte budget only, with eviction on one file.** This bounds the file, but every append still parses and rewrites the whole collection, and the budget has to stay below a quarter of the bound. It is kept as a second limit (`maxBytes`, `maxRecordBytes`), not as the layout.
- **Streaming the whole file through `parseNotation`.** `links-notation`'s `StreamParser` with `collect: false` parses without keeping the document, and it is used for the one-time migration. The mirror still has to stage and project a file, so chunking is what keeps each projection bounded.
- **Raising `MAX_NOTATION_LENGTH`.** V8 cannot hold a string much over 2^29 characters, about 1 GiB of one-byte text ([V8 change](https://chromium.googlesource.com/v8/v8/+/refs/tags/8.1.307.5%5E), [Node.js issue 9489](https://github.com/nodejs/node/issues/9489)), and 40 sources were extrapolated to about 1.3 GB. Rejected.
- **Reusing the offer chunk store.** Offer chunks carry offer-specific bounding, variants and sub-shards. The shared parts (durable writes, pruning, digests) moved to `src/chunk-files.js`, and both layouts use them.
