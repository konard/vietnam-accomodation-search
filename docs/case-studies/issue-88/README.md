## Issue 85: offers bounded only on read

Root causes, confirmed on main:

1. `LinksStore#readOffers` bounded stored offers, but `saveOffers` appended the **unbounded** `incoming` offers before writing. `#saveRecords('offers')`, `updateRecords('offers')` and `writeOfferCollection` did not bound anything. A replayed checkpoint batch therefore wrote its GramJS `Photo` objects in full. One such offer formats to 4,090,189 bytes of LiNo with 39,600 `/bytes/data/N` links, and 6,158 bytes once bounded (`experiments/issue-85-replayed-offer-size.mjs`).
2. `writeOfferCollection` returned from its single-file branch before the step that prunes unindexed `offers.chunks/*`.
3. `writeShards` rewrote and restaged every chunk on every save. Chunk directories are content-addressed, so the chunk holding an edited offer is a new directory with an empty `.binary`. All of its sub-shards were imported again, including the unchanged ones.
4. `deduplicateVariants` keyed variants on `(id, sourceId, collectedAt)`. Each recollection of the same message therefore added another variant, and the price history grew without limit.

### Measurements

All runs use synthetic listings on the development host. The real `clink` was 0.2.11 at `/tmp/clink/bin`, with the default shard sizes (32/64/128 links).

| Scenario (`experiments/issue-85-real-clink-reuse.mjs 600 600000`) | main `f8ec324` | this branch |
| ----------------------------------------------------------------- | -------------: | ----------: |
| First save: 600 listings, 16 chunks, 497 databases (`clink` runs) |            497 |         497 |
| Edit one listing: `clink` runs                                    |             37 |           1 |
| Following read: `clink` runs                                      |              0 |           0 |

With the stub `clink` from `experiments/issue-85-projection-timing.mjs`, an edit of 40 listings in 273 tiny sub-shards takes 2 runs and about 0.5 s. One replayed pre-#82 offer drops from 4,090,189 to 6,158 bytes of LiNo.

The protected run in the issue saw 51,741 projections for 6 checkpoints. Main reprojected every sub-shard of every chunk that one batch touched. On this branch only the sub-shards with new content are projected, and the oversized pre-#82 offers are bounded before their first write. The expected effect on the 16-hour estimate is therefore large, but it is not measured until 85.4 runs.

### Options considered

- **Content-defined deduplication by digest**, as in restic: only blobs whose content hash is new are stored ([restic CDC](https://restic.net/blog/2015-09-12/restic-foundation1-cdc/), [rustic design notes](https://rustic.cli.rs/dev-docs/design/backups_deduplication.html)). The mirror already splits by content and addresses shards by SHA-256. What was missing was a lookup across chunk directories, so this branch adds one instead of a new store.
- **One shared shard store for all chunks.** This would avoid adoption altogether. It changes the on-disk layout, the snapshot rules that exclude `.binary`, and the pruning rules. Rejected for this patch.
- **Hard links with a copy fallback.** Hard links cannot cross devices and fail with `EXDEV` ([techoverflow](https://techoverflow.net/2023/03/14/how-to-fix-nodejs-error-exdev-cross-device-link-not-permitted-rename/)), so the mirror copies in that case. Linked files are safe because the mirror never modifies a projection file in place: every build happens in a fresh directory, and old ones are renamed aside.
- **Batching the audit's saves.** This lowers the number of saves, but not the work per changed chunk. It is left to the audit harness, because the store fix applies to every caller.
