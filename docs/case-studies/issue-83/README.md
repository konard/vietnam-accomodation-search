## Issue 77: data directory on redeploy

Root cause, confirmed on main: `validateDataDirectory` ran `mkdir(directory, { recursive: true })` for any accepted path. Only `rollback` compared the path recorded in `.deploy/PROJECT/state.json`; `deploy` did not.

| ID   | Requirement                                                                                             | Solution and evidence                                                                                                                                                                                                                                                                                                                                                                     |
| ---- | ------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 77.1 | Refuse a different `dataDirectory` for a recorded project before building or stopping; name both paths. | `planDataDirectory` in [deploy-guards](../../../scripts/deploy-guards.mjs) runs right after options are read, before the port check, image pull or build, and `stop`. The error reads `The recorded deployment uses data directory OLD, not NEW. Pass --move-data-directory to move the deployment to NEW.`                                                                               |
| 77.2 | Never create a missing directory for a recorded project; a first deploy reports the one it creates.     | `validateDataDirectory(path, { create })` only creates when the plan allows it, which is a first `deploy` only. With `--move-data-directory` a missing target is still refused. A first deploy prints `Created data directory PATH`. `status` and `logs` never create a directory.                                                                                                        |
| 77.3 | Refuse an empty or unmarked directory when the previous one had data; allow an explicit override.       | `inspectDataDirectory` reads the directory without changing it. A target that lacks `.state-schema.json` or holds no data is refused while the recorded directory holds data, unless `--allow-empty-data-directory` is passed. The project's own directory losing its marker is refused too: the marker and `state.dataDirectory` both date from #57, so every recorded deploy wrote one. |
| 77.4 | Regression tests: typo, different existing path, first deploy, migration flag.                          | [tests/issue-77-data-directory.test.js](../../../tests/issue-77-data-directory.test.js): 11 tests, including on-disk inspection and a check that drill cleanup removes the record.                                                                                                                                                                                                        |
| 77.5 | Document the behavior.                                                                                  | [Safe redeploy](../../deployment.md) and the restore and named-volume migration sections.                                                                                                                                                                                                                                                                                                 |

The message-level cutover drill reuses one `--project-name` with a new data directory for each run. Its cleanup now removes `.deploy/PROJECT/state.json` and `snapshots/` after `docker compose down` succeeds. Without that, the next run's `first-deploy` would be refused as an unrecorded move.

## Issue 78: two pollers on one bot token

Root cause, confirmed on main: `src/telegram-errors.js` classified a 409 as `fatal`, so the process exited. With `restart: unless-stopped`, two instances kept evicting each other. Nothing cleared readiness after `onStart`, and `deploy` looked only at its own project.

| ID   | Requirement                                                                                                                        | Solution and evidence                                                                                                                                                                                                                                                                                                                                                                                     |
| ---- | ---------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 78.1 | A conflict marks the instance unready at once; `/ready` is non-200 and the healthcheck fails.                                      | `TelegramRuntime` returns `/ready` 503 `{"status":"not-ready","reason":"polling-conflict","conflicts":N}` from the first conflict until a later `getUpdates` succeeds. The Docker healthcheck probes `/ready`.                                                                                                                                                                                            |
| 78.2 | No endless restart loop; bounded, jittered backoff with a clear message.                                                           | `CONFLICT_BACKOFF` runs from 5 s to 5 min, exponential with jitter. Each conflict logs `telegram polling conflict: another poller holds this bot token`, and recovery logs `telegram polling resumed`. A 409 before readiness still exits with code 21, so a new deploy fails fast instead of waiting.                                                                                                    |
| 78.3 | After cutover, observe a settle window; on a 409 or restart, fail and restore without printing `Deployment healthy`.               | `observeSettle` samples `docker inspect` and the candidate's logs for `--settle-seconds` (default 30; `0` disables). A conflict, restart, stop, or `unhealthy` status throws inside `deploymentStateMachine`, which restores the previous image and snapshot. `Deployment healthy` is printed only after the window passes.                                                                               |
| 78.4 | Guard against sharing a token across projects using a hash, never the token; `--allow-shared-token`; document separate drill bots. | `TOKEN_FINGERPRINT_SCRIPT` runs inside the candidate image with the project's environment and prints only `sha256("telegram-bot-token:" + token)`. The token never reaches the host process or its logs. `state.json` records the digest. `assertTokenNotShared` refuses a digest that another `.deploy/*` project recorded, unless `--allow-shared-token` is passed.                                     |
| 78.5 | Regression test: two pollers, unready, non-zero deploy exit.                                                                       | [tests/issue-78-polling-conflict.test.js](../../../tests/issue-78-polling-conflict.test.js) runs two `TelegramRuntime` instances against one fake Bot API token hub. The evicted instance's `/ready` reports `polling-conflict`. Its real log lines feed the deploy settle window, which rejects with `… 2 s settle window: N Telegram polling conflict(s) …` after the calls `stop`, `start`, `restore`. |

The fingerprint guard only covers projects deployed from the same checkout. Another host cannot be seen from here, and the runtime backoff plus the settle window are the defenses in that case.

## Issue 82: raw media objects in offers

Root cause, confirmed on main: `mediaIdentity()` fell through to `message.media`. A GramJS `MessageMediaPhoto` keeps its ID in `.photo.id`, so whole objects, thumbnail bytes included, became "photo IDs". Each object was then serialized one link per byte in `photos`, `raw`, `variants[0].photos`, and `variants[0].raw.photos`.

| ID   | Requirement                                                                                                                      | Solution and evidence                                                                                                                                                                                                                                                                                                                                     |
| ---- | -------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 82.1 | `mediaIdentity` returns a stable scalar; tests use GramJS and mtcute shapes.                                                     | Returns `photo.id` or `document.id` as a string for GramJS, mtcute raw TL, and normalized mtcute media. Album IDs are deduplicated and capped at 10. See [experiments/issue-82-gramjs-media-shape.mjs](../../../experiments/issue-82-gramjs-media-shape.mjs) and [tests/issue-82-bounded-offers.test.js](../../../tests/issue-82-bounded-offers.test.js). |
| 82.2 | No binary or raw provider objects persisted; a per-offer budget test.                                                            | [src/offer-bounds.js](../../../src/offer-bounds.js) keeps an allow-listed, JSON-safe `raw` within 8 KiB, 4096-character strings, 20-item arrays, and depth 4. A test asserts that a ten-photo GramJS album offer contains no `Buffer` or `Uint8Array` and stays within the per-offer budget.                                                              |
| 82.3 | Migrate existing oversized collections and chunks; bump the schema if needed.                                                    | `LinksStore.migrateOffers` rewrites legacy offers at startup, and reads return the bounded shape. The schema was not bumped: on main, `photos` is already read as strings (URLs or file IDs) by `media-cache.js` and `telegram-bot.js`, so the previous release reads migrated data correctly, and rollback stays safe.                                   |
| 82.4 | A failed or interrupted save removes or reuses its own unindexed chunk directories.                                              | A failed save removes the chunk directories it created. The next save prunes unindexed leftovers before writing, but not when the index is unreadable. Four tests cover this.                                                                                                                                                                             |
| 82.5 | The protected 40-source audit completes within 6 GiB / 15 GiB free; record size, files, duration; a second run reuses the cache. | Not run here: the retained private corpus and the GramJS session are absent from this workspace. Run `experiments/diagnose-telegram-audit.mjs` against a protected copy. The issue's sample measured 2.2 MB per offer; the 8 KiB `raw` limit and scalar `photos` bound that growth.                                                                       |
