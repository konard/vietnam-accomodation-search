## Research and component choices

- **Projection throughput.** The pinned [`clink` 0.2.10 storage](https://github.com/link-foundation/link-cli/blob/rust-v0.2.10/rust/src/link_storage.rs) implements `search(source, target)` (line 573) as a filter over `self.links.values()`, and `get_or_create` (line 593) calls it for every imported reference. Updates also pass through the uniqueness and usages resolution decorator. Import therefore costs time linear in the store for every link, which is quadratic for the whole import. A fresh measurement agrees: 512 links took 7.3 s and 1,024 links took 25 s. No upstream issue about indexing or import performance exists; a draft is included [below](#draft-upstream-link-cli-issue) and has not been filed.
- **Content-defined chunking.** [FastCDC (USENIX ATC '16)](https://www.usenix.org/conference/atc16/technical-sessions/presentation/xia), [restic's chunker](https://github.com/restic/chunker), [casync](https://github.com/systemd/casync), and [Borg](https://borgbackup.readthedocs.io/en/stable/internals/data-structures.html) all choose boundaries from content with minimum/average/maximum chunk sizes, so one edit only changes nearby chunks, and they address chunks by cryptographic digest for reuse. The same idea bounds every `clink` database here. Boundaries are chosen only between whole top-level links from an [FNV-1a](https://en.wikipedia.org/wiki/Fowler%E2%80%93Noll%E2%80%93Vo_hash_function) hash of each link id, so a byte-level [rolling hash](https://en.wikipedia.org/wiki/Rolling_hash) and a chunking dependency are unnecessary. Those libraries chunk opaque bytes and cannot guarantee that a boundary never splits a link.
- **links-notation input bound.** [`links-notation`](https://github.com/link-foundation/links-notation) `Parser` rejects inputs over 10,485,760 characters by default. The real 16 MiB first-source snapshot exceeds that, so this failure sat behind the projection timeout. `experiments/parser-size-limit.mjs` reproduces the rejection and the successful bounded parse.
- **Alternatives rejected.** Raising the 600-second deadline leaves quadratic growth. The transactional `clink` modes were already measured as slower in the [Issue #50 diagnosis](../issue-50/README.md#projection-throughput-diagnosis-2026-09-27). Rust `clink` 0.2.11 does not change the importer. An unverified JSON mirror would break LiNo authority. Forking `link-cli` to add an index remains the upstream fix, and this repository cannot pin it until a release exists.
- **Publication.** [npm trusted publishing](https://docs.npmjs.com/trusted-publishers/) still requires an existing package, so the first publish needs the owner's scoped bootstrap `NPM_TOKEN`. The 2026-09-28 preflight run [36432419599](https://github.com/konard/vietnam-accomodation-search/actions/runs/36432419599) confirmed that it is empty.

## Sharded, verified projection

Collections with more than 128 top-level links are cut into content-defined shards of 32 to 128 links, averaging about 64. The shards must concatenate byte-for-byte to the canonical text, otherwise the collection falls back to one database. Every shard is imported into its own `.binary/KIND.shards/SHARD-HASH` database with up to four concurrent `clink` processes. Its complete export is verified link-by-link before a manifest records SHA-256 digests of the database, names database, and verified export. The collection manifest lists shard hashes in order. A later save reuses a shard only if all three digests still match, and imports only changed shards. A failed or interrupted projection keeps its completed shards, because only pointer activation prunes. The next attempt resumes from them, and at most three `.failed-*` diagnostics are retained per directory. Progress reports only aggregate `completed`, `reused`, and `total` counts. Reading decodes through one id index and one owner index instead of scanning every link for each record and field.

### Measurements (synthetic, aggregate only)

Host: 6 vCPU AMD EPYC, 11 GiB RAM, Node 24.21.0, `clink` 0.2.10, concurrency 4. Reproduce with `CLINK_COMMAND=… node experiments/measure-sharded-projection.mjs --records N` and `node experiments/measure-deserialize.mjs`.

| Offers | Links  | Text     | Shards | Cold projection       | Unchanged save  | One-offer edit (reused) |
| ------ | ------ | -------- | ------ | --------------------- | --------------- | ----------------------- |
| 100    | 2,101  | ~0.24 MB | 33     | 3.5 s (single: 111 s) | 0.4–0.7 s       | 1.2–1.4 s (32)          |
| 2,000  | 42,001 | 4.8 MB   | 647    | 76.7 s; 99.9 s²       | 11.9 s; 13.9 s² | 9.9 s; 10.9 s² (646)    |
| 4,000  | 84,001 | 9.75 MB  | 1,290  | 220 s¹                | 22 s            | 20.9 s (1,289)          |

¹ Measured while another benchmark shared the CPU. ² Rerun under `experiments/sample-tree-rss.sh`, which sampled a peak resident set of about 400 MiB (405,528 KiB) for the whole process tree.

Cold time now grows linearly with the number of shards. A single database grows quadratically, and 2,101 links alone took 111 s. The 10-minute deadline now applies to each shard's `clink` process, which handles at most 128 links. Extrapolated linearly, a 16 MiB collection needs roughly 5–6 minutes and about 1.4 GiB for its first projection, then seconds for each incremental save. The budget is documented in [storage](../../storage.md#binary-projection-and-commit-protocol) and must be confirmed on the private corpus.

## Draft upstream link-cli issue

Not filed; post it only with the maintainer's approval.

> **`LinkStorage::search` scans every link, making `clink` import quadratic.** In `rust/src/link_storage.rs` (tag `rust-v0.2.10`), `search(source, target)` filters over `self.links.values()`, and `get_or_create` calls it for every reference during LiNo import. Importing N links is therefore O(N²): 512 links take 7.3 s and 1,024 take 25 s on a 6-vCPU host, and a 16 MiB collection does not finish in 10 minutes. Proposal: maintain a `HashMap<(u32, u32), BTreeSet<u32>>` (or a minimum index) updated in `create`, `update`, and `delete`, so `search` is O(1) average. Export has a similar per-link scan worth checking.
