## Root causes, alternatives, and selected solutions

### Identity (#146)

`offerIdentityKeys` correctly emits distinct source-property keys, but the old union-find algorithm merged on any shared key. A location/contact/area/bedroom fingerprint therefore erased contradictory explicit unit evidence. The same failure reached `LinksStore.saveOffers` and `SearchService` because both use shared reconciliation.

Adding property IDs/floors to every fingerprint is a small alternative, but it prevents otherwise legitimate repost matching when one source omits those fields or uses a different source-specific identifier. Pairwise conflict checks during a single union pass are also insufficient: an unidentified record can bridge incompatible roots, and processing weak evidence before strong aliases makes the outcome depend on traversal order.

The selected algorithm resolves strong aliases first, retains explicit identity constraints for entire groups, and then processes weak fingerprint candidate groups. A contradictory namespace or unit field makes that weak group ambiguous, so the fingerprint does not merge it. An unidentified bridge consequently cannot erase distinct units. Candidate ambiguity uses intersections per constraint namespace rather than all-pairs comparisons. Learned source-property/external keys keep constraints after bounded variants rotate out. Source-property keys are generated from each retained source variant, avoiding assignment of one source's unit ID to another source after a cross-source merge.

This is deliberately conservative where one agent supplies several distinct units and a third post omits its identity. The unidentified post stays separate until stronger evidence establishes its unit. Already lost variants from historical false merges cannot be reconstructed from missing data; preserved raw source histories can be re-ingested after this fix.

### Chronology (#147)

The old merge sorted only by `collectedAt`. Telegram history batches share one collection time; stable sorting left descending source history in descending order, so the last/oldest post controlled availability and current per-source price. A collection timestamp describes observation, while `postedAt` and the last edit describe source state.

Sorting history ascending at one acquisition call site would miss other collectors, incremental persistence, learned groups, and price histories. Using only post time would miss later edits to an older post. Increasing collection times artificially would fabricate source chronology.

The selected shared comparator uses the latest known publication/edit/update time, with observation time as fallback or a same-source-state tie breaker. Known-time ties use stable record identity/content. Undated legacy records retain their existing replacement order. Explicit edit timestamps are promoted into normalized `updatedAt`, retained on variants and price observations, and recognized from provenance/legacy raw records. Saved legacy price observations recover missing source dates from matching retained variants. Aggregate `collectedAt` remains the latest actual observation for cache freshness. ISO/Date/Unix-second edit normalization also fixes inconsistent timestamp comparison in the history collector and album assembly. Albums retain the latest member edit; independent captions retain their own edits rather than inheriting another caption's date.

### Publication (#122)

The existing pipeline already requires native images, tests the published npm version, and assembles immutable release evidence. Fresh read-only checks return empty repository secret names, variable names, and release lists; the registry package is absent. Local release-mode preflight exits 1 with 0 verified, 2 failed, 1 unknown (local OIDC unavailable). This cannot be resolved by a code-only patch or a different Telegram test account.

The operational solution is authorized configuration: bootstrap `NPM_TOKEN`, `DOCKERHUB_IMAGE`, `DOCKERHUB_USERNAME`, and `DOCKERHUB_TOKEN`, followed by the existing exact-commit release workflow. Subsequent npm publication can use a configured trusted publisher. A GHCR-only migration or skipping OCI publication would change the stated acceptance contract, so neither is used. Keep #122 acceptance unmet until the exact release SHA publishes all artifacts and the published clean install and native manifests/digests are verified. The parent-required closing references are merge mechanics, not proof of this gate; merging before those prerequisites exist would close an unresolved acceptance issue again.
