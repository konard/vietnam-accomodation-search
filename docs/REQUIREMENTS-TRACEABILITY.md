# Product requirement traceability

This document is the durable checklist for the requirements originating in
[Issue #1](https://github.com/konard/vietnam-accomodation-search/issues/1) and
the 2026-09-22 deployment, Telegram, subscription, parsing, and associative-stack
follow-up. An issue may close only when its requirement has code, automated
tests, documentation, and sanitized live evidence where applicable.

Status meanings:

- **Verified** — observed in the 2026-09-22 baseline or already covered by a
  durable test.
- **Partial** — a scaffold or experiment exists, but the production acceptance
  criteria are not complete.
- **Open** — owned by an issue and not yet demonstrated end to end.

## Telegram reference practices

The production contracts deliberately adopt and improve the strongest patterns
from the three reference repositories:

- `telegram-bot`: interactive phone/code/2FA authentication with cleanup in
  `finally`, help parsing before connection, Telegram flood-wait handling, and
  broad event/entity extraction. Exact references are recorded in
  [#6](https://github.com/konard/vietnam-accomodation-search/issues/6),
  [#7](https://github.com/konard/vietnam-accomodation-search/issues/7), and
  [#9](https://github.com/konard/vietnam-accomodation-search/issues/9).
- `follow`: hidden 2FA and first-run session creation, reusable connected user
  clients, entity refresh with bounded retries, and cleanup that retries and
  aggregates failures. Exact references are recorded in #6, #7, and #9.
- `telegram-terminal-bot`: credential validation, authorization middleware,
  bot-level error handling, signal handling, and startup hooks. Exact references
  are recorded in #6 and #9; this project additionally requires awaited graceful
  shutdown instead of immediate process exit.

These are floors, not ceilings: ambiguous non-idempotent sends must not be
replayed, private update payloads must not be logged, sessions need stronger
storage than a normal plaintext `.env`, and capability fallback must be typed
and observable.

## Evidence update policy

Edit this document and the owning issue bodies when evidence changes. Do not use
status-only issue comments. Never mark **Verified** solely because code exists;
the corresponding tests and, where applicable, sanitized live run must pass.
